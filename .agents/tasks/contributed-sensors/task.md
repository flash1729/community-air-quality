Project root /home/vishwas/Desktop/CC/community-air-quality (backend FastAPI/Python/SQLite in /home/vishwas/Desktop/CC/community-air-quality/backend, frontend React+TypeScript in /home/vishwas/Desktop/CC/community-air-quality/frontend). HEAVY task: multiple subsystems.

Goal: Let individuals, residents, schools and communities register their air quality devices and contribute measurements to the EXISTING Community Sensor Network. Core flow: User registers sensor -> Device reports measurements and coordinates -> Backend processes and stores -> Frontend displays sensor and readings.

1. Registration: user clicks 'Add Sensor' and provides ONLY: sensor name, hardware ID, hardware model (e.g. ESP32 + PMS5003), contributor name. DO NOT ask for location/latitude/longitude. Backend generates a unique application sensor ID (e.g. SENSOR_011) and the required connection configuration (ingestion endpoint URL, sensor id, any auth/key as fits existing architecture).

2. Reading payload (each reading must contain): sensor_id, sequence_number, pm25, pm10, temperature, humidity, latitude, longitude, recorded_at (device timestamp). Example: {"sensor_id":"SENSOR_011","sequence_number":1052,"pm25":42.5,"pm10":68.2,"temperature":29.4,"humidity":65.0,"latitude":12.9352,"longitude":77.6245,"recorded_at":"2026-11-13T08:30:00Z"}. Backend validates coordinates (range, finite) and associates them with the sensor. Store the latest reported coordinates as the sensor's current location and PRESERVE historical measurement records. Do not assume every ESP32/PMS5003 has GPS; in a future physical build location may come from GPS or another provisioning mechanism.

3. Backend: register sensors without location; generate unique IDs; receive measurements incl. coordinates; validate measurements and coordinates; store sensor metadata and measurement history; update latest known location; determine online/offline from last successful report; return sensor info and location to frontend.

4. Frontend: Add Sensor form has exactly 4 fields (name, hardware ID, hardware model, contributor name). After registration and first successful reading: show sensor on Community Network map at reported coordinates; latest PM2.5 and PM10; current location; historical measurements and charts; connection status. Before the first valid location-bearing reading, show the sensor as 'Awaiting first data' and NOT on the map at an arbitrary location. Data and charts update automatically (polling/refresh).

5. Python virtual sensor agent (new script in /home/vishwas/Desktop/CC/community-air-quality/backend, update /home/vishwas/Desktop/CC/community-air-quality/backend/SIMULATOR_QUICKSTART.md): represents an independently registered physical device; receives its generated sensor ID and connection config (CLI args/env/config); keeps an internally configured geographic location (user never types coordinates in UI); generates realistic changing measurements; includes lat/lon in every reading; submits via HTTP to the actual FastAPI ingestion endpoint; keeps reporting periodically. MUST NOT write to SQLite directly and the frontend must not generate data.

6. Constraints: PRESERVE the existing ten Bengaluru sensors and their behavior; reuse existing database and ingestion architecture; user-added sensors live in the same Community Network; no manual location entry; keep simulated/user-added and existing sensor data distinguishable (e.g. a source/origin field and UI badge); everything must work locally before cloud deployment (no cloud-only dependencies).

7. Demonstration: click Add Sensor -> enter 4 fields -> backend registers & returns app sensor ID -> simulator starts reporting measurements+coordinates -> backend validates/stores -> sensor appears at reported location on map -> measurements and charts update automatically.
