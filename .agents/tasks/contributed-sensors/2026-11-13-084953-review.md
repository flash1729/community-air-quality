# Community-Contributed Sensor Network Implementation

User-contributed sensors join the existing Bengaluru network through a 4-field registration form. Sensors report location with each measurement rather than at registration. Backend validates coordinates, stores them per reading, and updates the sensor's current location. The frontend shows "Awaiting first data" until coordinates arrive, then places the sensor on the map with a "Community Contributed" badge.

**Watch for:** (confirmed) Simulator coordinates come from backend API metadata, not from the device's internal config as specified. (confirmed) Sequential sensor ID generation has a race condition gap between query and insert. (likely) Registration endpoint returns token in JSON without rate limiting.

**Verdict**: NEEDS_CHANGES

---

## High-level view

Registration creates sensors with null coordinates and source='contributed'; the first reading with coordinates triggers map placement. Sequential IDs (SENSOR_011, SENSOR_012) use retry logic to handle collisions, but the 3-attempt window doesn't eliminate the race—two concurrent requests can query the same max ID before either commits. The readings endpoint requires coordinates for contributed sensors and updates the sensor's location field, so the latest location is always available without querying the readings table. The simulator fetches sensor metadata from the API and includes those coordinates in every reading, meaning it doesn't maintain an "internally configured geographical location" as the task specified—it echoes the backend's coordinates back to the backend. The map endpoint filters sensors with null coordinates so sensors awaiting data don't appear. Token security follows bcrypt hashing but the 201 response includes the plaintext token with no rate limiting, so an attacker can register unlimited sensors and exhaust ID space or fill the database. The migration recreates the community_sensors table to make latitude/longitude nullable, preserving existing data with source='seed'.

## Registration without location

POST /api/v1/community/sensors/register accepts 4 fields: name, hardware_id, hardware_model, contributor_name. No latitude or longitude. The endpoint generates a sequential sensor ID (SENSOR_011, SENSOR_012) by querying `MAX(CAST(SUBSTR(id, 8) AS INTEGER))` and incrementing. If the ID already exists (IntegrityError), it retries up to 3 times.

The race condition: two concurrent requests both query the max ID, both get SENSOR_010, both generate SENSOR_011, both try to insert. The first succeeds, the second gets IntegrityError and retries, but by then both are on attempt 2. If traffic is high, all 3 attempts can collide. The retry logic reduces the probability but doesn't eliminate the race. A database-level sequence or UUID would fix it.

The sensor is created with latitude=None, longitude=None, source='contributed', sensor_type='contributed'. A 32-byte token is generated via secrets.token_urlsafe(32), hashed with bcrypt, stored in auth_token_hash. The plaintext token is returned in the 201 response along with sensor_id and ingestion_url. The response body contains the token in plain JSON, which may be logged by proxies, load balancers, or browser devtools. This is unavoidable for the registration flow (the token must be delivered to the user somehow), but it's a reminder that HTTPS is mandatory and logging should redact the response body.

No rate limiting on this endpoint. An attacker can POST repeatedly and exhaust sensor IDs (SENSOR_999 is the practical upper limit for the 03d format, though the format could go higher) or fill the database with junk sensors. Even with bcrypt slowing down each request, a determined attacker can register hundreds of sensors before noticing. Rate limiting by IP or requiring CAPTCHA would mitigate this.

AddSensorModal shows the 4-field form, validates client-side (required, max lengths), submits to /api/v1/community/sensors/register. On success, displays a success view with sensor_id and token in monospace text with copy-to-clipboard buttons. A yellow warning box says "Store these credentials securely. The authentication token cannot be retrieved later."

## Coordinates in readings and location updates

CommunitySensorReadingSubmit schema adds latitude and longitude as optional floats. The submit_reading endpoint checks if sensor.source == 'contributed' and raises 400 if latitude or longitude is None. For any sensor (seed or contributed), if coordinates are provided, validates:

- math.isfinite(latitude) and math.isfinite(longitude) to reject NaN or Inf
- -90 ≤ latitude ≤ 90
- -180 ≤ longitude ≤ 180

If coordinates pass validation, they're stored in the CommunitySensorReading row (historical record) and copied to sensor.latitude and sensor.longitude (current location). This means the sensor's location field is always the latest reported coordinates, not the original registration location (which doesn't exist for contributed sensors).

Seed sensors (source='seed') can submit readings without coordinates. The readings endpoint only requires coordinates for source='contributed'. This asymmetry is intentional: seed sensors were created with fixed coordinates in the database, so their location is already known. Contributed sensors have no location until the first reading arrives.

Temperature validation was added: -40 to 60°C.

The map endpoint filters sensors with `where(CommunitySensor.latitude.is_not(None)).where(CommunitySensor.longitude.is_not(None))`. Sensors with null coordinates are excluded from the map response. This implements the "Awaiting first data" state: sensors don't appear on the map until they report coordinates.

## Simulator coordinates source mismatch

The task says "maintain an internally configured geographical location" and "generate changing air quality measurements" with "latitude and longitude in every reading". The implication is that the simulator has a config file or command-line arg specifying the sensor's location (e.g., `--latitude 12.9352 --longitude 77.6245`), and it includes those coordinates in every reading.

What the code does: VirtualSensor loads sensor tokens from sensor_tokens.json, calls GET /api/v1/community/sensors to fetch metadata, extracts latitude and longitude from the API response, stores them as self.latitude and self.longitude, and includes them in the reading payload.

For a newly registered contributed sensor, the API returns latitude=None, longitude=None. The simulator would set self.latitude = None, self.longitude = None, and include those in the reading. But the readings endpoint requires coordinates for contributed sensors, so the first reading would fail with 400 "Latitude and longitude required for contributed sensors."

The verification doc says "The simulator loads location coordinates from the backend API. For contributed sensors, the first reading updates the sensor's location on the backend, which the simulator then uses for subsequent readings." This describes a chicken-and-egg problem: the simulator needs coordinates to submit the first reading, but the backend doesn't have coordinates until the first reading arrives.

The solution implied by the docs: manually edit the database or the sensor record to set initial coordinates, then the simulator fetches them and submits readings. But this bypasses the "sensor reports its location" design. The task says "simulator should maintain an internally configured geographical location" and "user never types coordinates in UI"—meaning the simulator has the coordinates, not the backend.

The code as written requires manual intervention (editing the database to set coordinates before running the simulator, or submitting the first reading via curl with coordinates manually specified). The task spec implies the simulator should have coordinates from the start, independent of the backend.

## Sequential sensor IDs and ID collision retry

The registration endpoint generates sensor IDs by querying the max numeric suffix and incrementing. The query uses raw SQL via `db.execute(text("SELECT MAX(CAST(SUBSTR(id, 8) AS INTEGER)) FROM community_sensors WHERE id LIKE 'SENSOR_%'"))`. This works for SQLite but isn't portable (SUBSTR and CAST syntax vary by database).

The next_num calculation uses `(max_num or 10) + 1`, so the first contributed sensor is SENSOR_011.

If two requests run this query concurrently before either commits, both get the same max_num and generate the same sensor_id. When both try to INSERT, one succeeds and the other gets IntegrityError (primary key violation). The retry logic catches IntegrityError, rolls back, and tries again. After 3 attempts, it raises 500 "Failed to generate unique sensor ID after multiple attempts."

The retry reduces the collision probability but doesn't eliminate the race. If traffic is high, or if an attacker deliberately sends concurrent requests, all 3 attempts can collide, causing legitimate registrations to fail with 500.

A database-level sequence or auto-incrementing column would be atomic. SQLite doesn't support sequences, but SQLAlchemy can simulate one with a separate table and SELECT FOR UPDATE. Alternatively, switch to UUIDs (sensor_id = str(uuid.uuid4())) and drop the SENSOR_* pattern. The plan says "UUID deferred to production," which is fine for MVP, but document that the sequential ID approach is not production-ready under concurrent load.

## Source distinguishing and badge display

Sensors have a source field ('seed' or 'contributed') added by the migration. The migration copies existing sensors with source='seed'. The seed script (seed_community_sensors.py) was updated to set source='seed' explicitly and to update existing sensors if source is NULL or empty.

The frontend CommunitySensorMap filters valid sensors (latitude !== null && longitude !== null), then renders markers. In the marker popup, if source === 'contributed', a blue badge "Community Contributed" is rendered below the status badge.

SensorDetails also shows the badge and, if source === 'contributed', displays hardware_id, hardware_model, and contributor_name in the metadata list.

## Awaiting first data state

CommunitySensor schema changes latitude and longitude from `Mapped[float]` to `Mapped[float | None]`. The frontend types.ts changes latitude and longitude from `number` to `number | null`.

SensorDetails checks `if (sensor.latitude !== null && sensor.longitude !== null)` before rendering the coordinates. If either is null, it renders `<span className="italic text-muted">Awaiting first data</span>` instead of the lat/lon display.

One edge case: a contributed sensor that has submitted readings without coordinates (e.g., a bug in the device firmware that omits lat/lon) would still show "Awaiting first data" even though readings exist. The message doesn't distinguish "never reported" from "reported but no coordinates." If seed sensors can submit readings without coordinates (they can, per the readings endpoint logic), a seed sensor's location could theoretically be null if the seed script failed. The UI would show "Awaiting first data" for a sensor that has historical readings.

## Migration and database schema changes

001_add_contributed_sensor_fields.sql recreates the community_sensors table to make latitude and longitude nullable (SQLite doesn't support ALTER COLUMN). Steps:

1. CREATE TABLE community_sensors_new with updated schema (source, hardware_id, hardware_model, contributor_name added; latitude and longitude nullable)
2. INSERT INTO community_sensors_new ... SELECT ... FROM community_sensors, setting source='seed' for all existing rows
3. DROP TABLE community_sensors
4. ALTER TABLE community_sensors_new RENAME TO community_sensors
5. CREATE INDEX ix_community_sensors_status (recreate the index)
6. ALTER TABLE community_sensor_readings ADD COLUMN latitude FLOAT; ADD COLUMN longitude FLOAT

The INSERT uses `'seed' as source, NULL as hardware_id, NULL as hardware_model, NULL as contributor_name`.

The migration doesn't verify that existing sensors have non-null latitude and longitude before the table recreation. If the pre-migration database has a sensor with null coordinates (shouldn't happen, but corruption or manual edits could cause it), the migration copies it as-is. After migration, the map endpoint filters out sensors with null coordinates, so that sensor would disappear from the map.

run_migration.py reads the SQL file, executes it with `conn.executescript(sql_content)`, then verifies the schema by querying PRAGMA table_info. The verification prints existing sensors and their source field but doesn't check coordinate validity.

## Database migration safety

The migration uses DROP TABLE and CREATE TABLE, which is destructive. The migration runner doesn't create a backup before executing. If the migration fails partway through (e.g., between DROP TABLE and ALTER TABLE RENAME), the original table is lost.

SQLite supports transactions, so the migration could wrap the entire script in BEGIN...COMMIT. If any step fails, ROLLBACK would restore the original state. The run_migration.py script uses `conn.executescript()`, which disables automatic transactions and issues an implicit COMMIT after each statement. This means the DROP TABLE commits immediately, before the RENAME, so a failure between those steps is not rolled back.

The migration could be made safer by wrapping the script in an explicit transaction or using conn.execute() with manual BEGIN/COMMIT. The verification doc doesn't mention backup/restore procedures.
