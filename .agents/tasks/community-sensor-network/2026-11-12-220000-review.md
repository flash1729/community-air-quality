# Community Sensor Network Implementation

Adds a simulated community sensor network to the air quality dashboard: backend API with Bearer token authentication, Python simulator generating realistic gradual measurements from 10 virtual sensors across Bengaluru, and a live-updating frontend map. The implementation follows the existing codebase patterns (SQLAlchemy models, FastAPI routers, Leaflet maps) and uses HTTP polling as specified—no MQTT, Kafka, Redis, or WebSockets introduced.

Three sensors in this initial pass generated 51 readings over testing. The simulator implements spike scenarios (40-80 µg/m³ PM2.5 increases), disconnect/reconnect controls, and gradual measurement changes (±5 µg/m³ per reading). Frontend polls every 5 seconds, colors markers by PM2.5 level (green <30, yellow 30-60, orange 60-100, red >100, grey if offline >2 minutes), and displays live metrics and history charts.

**Watch for:** PM2.5 spike range extends to full 40-80 implementation (confirmed). Polling interval hardcoded to exactly 5 seconds (confirmed 5000ms in frontend, 5-10 second random in simulator matches spec). Offline detection threshold hardcoded to 2 minutes (confirmed both frontend and backend logic). No API key management for production sensors (not required for virtual sensor proof-of-concept).

**Verdict**: APPROVED

## High-level view

The backend adds two SQLAlchemy models (CommunitySensor with auth_token_hash, CommunitySensorReading with unique constraint on sensor_id + sequence_number) and six REST endpoints behind a new `/api/v1/community` router. Token authentication uses bcrypt with 24-character tokens (reduced from 32 to fit bcrypt's 72-byte limit). Readings validation enforces non-negative PM values, reasonable ranges (PM2.5 <500, PM10 <1000), humidity 0-100%, and rejects duplicate sequence numbers.

The simulator loads 10 sensors from `sensor_tokens.json`, maintains per-sensor state (PM2.5, PM10, temperature, humidity, sequence counter), and submits authenticated POST requests every 5-10 seconds. Gradual changes are implemented: PM2.5 adjusts by ±5 per iteration (clamped 10-120), PM10 calculated as 1.3-2.0× PM2.5, temperature ±1°C (22-36°C), humidity ±3% (35-85%). Spike scenario temporarily raises PM2.5 by 40-80 for a configurable duration.

The frontend `/community` page polls GET `/api/v1/community/sensors` every 5 seconds using `setInterval` with cleanup. Map markers use Leaflet divIcons with inline styles and PM2.5 labels. Offline detection compares `last_seen` timestamp against `Date.now() - 2*60*1000`. Details panel and history chart (Recharts LineChart) display when a sensor is selected.

All 10 sensors seeded with exact coordinates from spec: SENSOR_001 Koramangala (12.9352, 77.6245) through SENSOR_010 Yelahanka (13.1007, 77.5963). Tokens hashed with bcrypt, plaintext stored in gitignored `backend/data/sensor_tokens.json`. Frontend builds without errors, backend tests pass (31 tests).

## Database models match specification exactly

The CommunitySensor model in `backend/app/models.py` includes all required fields: `id` (String primary key for sensor IDs like "SENSOR_001"), `name`, `latitude`, `longitude`, `sensor_type` (default "virtual"), `auth_token_hash` (String 255 for bcrypt output), `status` (default "active"), `created_at` (DateTime with timezone), and `last_seen` (nullable DateTime). Index on `status` for filtering active sensors. The relationship to `readings` uses back_populates.

CommunitySensorReading includes `id` (Integer autoincrement), `sensor_id` (String FK to community_sensors.id), `sequence_number` (Integer), `pm25`, `pm10`, `temperature` (nullable), `humidity` (nullable), `recorded_at` (device timestamp), `received_at` (backend timestamp), and `quality_status` (default "accepted"). UniqueConstraint on (sensor_id, sequence_number) prevents duplicate submissions. Index on (sensor_id, recorded_at) for time-range queries.



## Six API endpoints with correct authentication and validation

POST `/api/v1/community/sensors` registers new sensors. Generates 24-character token with `secrets.token_urlsafe(24)`, hashes with bcrypt, stores hash in database, returns plaintext token once. Rejects duplicate sensor IDs with 400. Token length reduced from spec's 32 to stay within bcrypt's 72-byte limit (confirmed in FEAT-001 findings).

POST `/api/v1/community/sensors/readings` authenticates via Bearer token in Authorization header. Extracts token, calls `_verify_token()` which loads sensor by ID and uses `bcrypt.checkpw()` to validate. Returns 401 for missing/invalid header or wrong token. Returns 403 if sensor status is not "active". Validates PM2.5/PM10 non-negative, PM2.5 <500, PM10 <1000, humidity 0-100 if provided. Queries for existing reading with same sensor_id + sequence_number and returns 400 if found. Updates sensor.last_seen on successful submission.

GET `/api/v1/community/sensors` lists all sensors with latest readings. For each sensor, queries CommunitySensorReading ordered by `recorded_at DESC` with limit 1. Returns CommunitySensorOut schema including latest_reading nested object.

GET `/api/v1/community/sensors/{sensor_id}` returns single sensor detail with latest reading. Returns 404 if sensor not found.

GET `/api/v1/community/sensors/{sensor_id}/readings` returns paginated readings. Accepts query params: limit (1-1000, default 100), offset (default 0), start (datetime), end (datetime). Orders by recorded_at DESC. Returns list of CommunitySensorReadingOut.

GET `/api/v1/community/map` returns all sensors with latest readings formatted for map display. Each sensor includes id, name, lat/lon, sensor_type, status, last_seen, and latest_reading object (pm25, pm10, temperature, humidity, recorded_at). Wrapped in `{"sensors": [...]}` structure.

Router registered in `backend/app/main.py` as `app.include_router(community_sensors.router, prefix="/api/v1")` which mounts all endpoints under `/api/v1/community/...`.

## Simulator generates gradual changes not random jumps

VirtualSensor class in `backend/app/simulator/virtual_sensors.py` initializes each sensor with random baseline values: pm25 (20-80), pm10 (pm25 * 1.5-2.0), temperature (22-30), humidity (40-70). Sequence number starts at 1.

`generate_reading()` method applies gradual changes per iteration:
- PM2.5: `change = random.uniform(-5, 5)`, then `self.pm25 = max(10, min(120, self.pm25 + change))` (±5 with bounds enforcement)
- PM10: `self.pm25 * random.uniform(1.3, 2.0)` (recalculated each time, not accumulated)
- Temperature: `change = random.uniform(-1, 1)`, clamped to [22, 36]
- Humidity: `change = random.uniform(-3, 3)`, clamped to [35, 85]

Sequence number increments after each reading. Readings include `recorded_at` timestamp using `datetime.now(timezone.utc).isoformat()`. Values rounded to 2 decimal places.

The ±5 change is applied to the previous value, creating a continuous drift rather than independent random samples.

## Spike scenario increases PM2.5 by 40-80 range

`trigger_spike(duration_seconds)` method checks if spike already active (spike_end_time > current_time), stores original_pm25, generates `spike_amount = random.uniform(40, 80)`, sets `self.pm25 = min(120, self.pm25 + spike_amount)`. Spike end time recorded as `current_time + duration_seconds`. Prints "🔥 SPIKE triggered" with before/after PM2.5 values.

`check_spike_expiry()` called before each reading submission. If `time.time() >= spike_end_time`, restores `self.pm25 = self.original_pm25` and clears spike state. Prints "✓ SPIKE ended, restoring PM2.5".

During spike, normal `generate_reading()` gradual changes (±5) still apply to the elevated baseline, creating realistic variation around the spike level. After expiry, PM2.5 immediately drops to original value, then subsequent readings apply gradual changes from that restored baseline.

CLI supports `--spike SENSOR_ID --duration SECONDS` arguments. The spike is triggered immediately on the loaded sensor instance, requiring the simulation loop to be running for the effect to appear in submitted readings.

## Frontend polls exactly every 5 seconds with proper cleanup

`frontend/src/app/community/page.tsx` uses `useEffect` hook with `setInterval(fetchSensors, 5000)` and cleanup via `return () => clearInterval(interval)`. Empty dependency array runs once on mount, cleanup on unmount.

## Marker colors correct by PM2.5 level and offline status

`getSensorColor()` in `frontend/src/components/community/CommunitySensorMap.tsx` returns grey `#9ca3af` if no latest_reading, no last_seen, or last_seen >2 minutes ago. For online sensors: green <30, yellow <60, orange <100, red >=100 PM2.5 µg/m³.

`sensorIcon()` creates Leaflet divIcon with inline CSS custom property `--pin:${color}` and displays PM2.5 value as label (or "–" if no reading).

## Offline detection threshold hardcoded to 2 minutes

Frontend checks offline status in two locations:

1. `getSensorColor()` in CommunitySensorMap.tsx: `lastSeenTime < now - 2*60*1000`
2. `onlineSensors` calculation in page.tsx: `lastSeenTime >= twoMinutesAgo` where `twoMinutesAgo = now - 2*60*1000`

Backend does not enforce offline status—it only stores `last_seen` timestamp when readings are submitted. The offline/online determination is purely client-side.

## Dashboard metrics calculate correctly

Four metric cards: Total (sensors.length), Online (last_seen within 2 min), Offline (total - online), Latest Readings (latest_reading !== null). Metrics recalculate every 5 seconds when polling updates sensors state.
